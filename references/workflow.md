# 目录清单与整理流程

按相对路径复制本 Skill 的 `assets/vault/` 文件。`.gitignore` 只在用户自己把库建成 Git 仓库时起作用，用来忽略系统文件和 Obsidian 的窗口布局缓存。遇到已有内容保留原文件。新库把默认新笔记设在收件箱，附件放系统底座，模板使用同名目录。已有库如要采用这些设置，可从 Obsidian 的「文件与链接」和「模板」调整。Bases 视图读取笔记文件和属性。 [管理仓库](https://obsidian.md/help/manage-vaults) · [Bases](https://obsidian.md/help/bases) · [导入 Web Clipper 模板](https://obsidian.md/help/web-clipper/templates)

## 整理与复查

收到「把这轮对话沉淀进知识库」时，用用户明确要留下的判断写一条新记录。注明来源为当前会话、指定导出文件或已有原文，只有能核实的链接才写入。区分用户决定、Agent 建议和未验证结论。用户指明项目就放进该项目，否则已确认的取舍进 `30-决策与复盘`，仍需确认的可先进收件箱。

- **归档预览**。确认用户点名的文件夹或资料，查看正文和发布日期、适用范围。给一张短表，包含库内或来源路径、动作、目标、理由和疑点。完全相同与内容相关是两种情况。保留重复的判断证据，并让用户决定是否合并。
- **确认后落盘**。外部资料复制入库，保留原件，注明用户可追溯的来源，避免在可分享笔记里留下私人设备路径。库内移动前检查目标存在与否、文件是否变更以及 Wiki 链接、Markdown 链接和附件引用。出现新冲突时暂停受影响项目。执行后确认旧路径、目标文件、引用与相关看板能对上。
- **追溯问答**。以导航为起点，阅读相关原始笔记，再简短引用相对路径与标题或段落。同一主题的记录有分歧时，给两份来源与确认状态，再说明能否裁定。日期优先记录真实发生日，未知就留空或在正文标注。
- **复查回填**。按「待复查」视图或实际属性找候选。先回读原决策和后续记录，再列已有证据、缺失项和下次复查。用户给出新事实时回填到原决策，保留旧判断。普通笔记靠看板查找，用户确认新的真源后再更新 `SOURCE_OF_TRUTH.md`。

推荐属性为 `日期`、`类型`、`状态`、`来源`，决策可加 `复查日期`。记录个人注意点、项目取舍、读书方法、生活体验或合作约定时，先写当时发生了什么、自己的判断和可核对的依据。后续再补实际结果。

归档确认后，把普通笔记的状态从「待整理」改为「已整理」，让它离开首页看板的「待整理」视图。决策保持「待复查」，直到补上实际结果。

## 维护节奏

用户平时只往收件箱放，分类、补属性、改导航和查冲突由 Agent 提出清单，用户确认。可复制的说法放在库内 `90-系统底座/常用口令.md`。

- **每天随手**。网页用 Web Clipper 存进收件箱，想法用 Obsidian 新建笔记，先不分类。Agent 不在这一步追问目录和标签。
- **每周清收件箱**。收件箱攒到五到十篇或到了每周固定时间，按归档预览给清单，确认后补属性、移动并刷新看板。收件箱积压过多时，可提议把一个月前的笔记整批移入 `80-已归档`，状态记为「已归档」，不逐条分类。
- **项目结项**。从 `10-进行中/项目名` 提炼能跨项目复用的经验，按知识卡片模板放进 `20-专业沉淀`，原项目移入 `80-已归档`，更新 `SOURCE_OF_TRUTH.md` 的入口。先给清单，确认后执行。目标是让 `10-进行中` 只留眼下在做的事。
- **决策回填**。用户给出实际结果时，补进原决策的「后来发生了什么」，按需更新「下次遇到相似情况」和复查日期。
- **每月只读体检**。检查失效的 Wiki 链接和 Markdown 链接、缺失附件、同一主题互相冲突的版本，以及导航是否过长或指向已归档的内容。只交清单，修复另行确认。
- **恢复点**。批量整理前提醒用户留恢复点，见 `AGENTS.md`。用户的库不是 Git 仓库时，不自行初始化。
